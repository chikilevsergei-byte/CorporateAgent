**Задача 2 — 🔴 Переработка работы с БД** ✅ согласовано пользователем.
Цель: сделать продуктивной **работу только с локальными/подключаемыми SQLite-файлами** и
**создание БД по файлам с помощью ИИ** (в интерфейсе и из чата). Код-привязки уточняются при реализации.

**2.1 Работа только с SQLite**
- Фокус/поддержка — **только SQLite** (`SqliteHelper`): локальные `.db` из `databases/` и «подключения»
  (`DbConnectDialog`, тип `sqlite`).
- В чипах БД чата и в списке БД показывать/допускать к выбору только записи с реальным существующим
  SQLite-файлом (`type=sqlite` и `path`/`file`).
- Серверные типы (PostgreSQL/MySQL/MongoDB/MSSQL/Oracle): скрыть из активного выбора или пометить
  «⚠️ нужен JDBC-драйвер», не допускать к запуску в чате / контуре A2 до добавления драйверов.
- Все чтение/запись идут через существующий `SqliteHelper` (уже реализовано).

**2.2 Создание БД по файлам (прямо в интерфейсе)**
- Экран создания БД (`DbManagerView`) получает блок **выбора нескольких файлов** «все поддерживаемые
  ИИ-форматы» — `.txt/.md/.csv/.html/.docx/.pdf/.xlsx/.pptx` (разбор через `FileExtractor`).
- Логика создания (главный путь вместо «введи SQL-схему руками»):
  1. `JFileChooser` (multi-select) → список выбранных файлов.
  2. Для каждого файла `FileExtractor.extractText` → накопление текстового содержимого (+ имена файлов).
  3. LLM (`llm.call` + отдельный промпт-«схема») по этому содержимому строит модель SQLite:
     список `CREATE TABLE` (типы, первичные ключи, связи, без `REFERENCES` как в `createDatabase`),
     при необходимости стартовые строки `INSERT` (для CSV/Excel — по заголовкам/строкам).
  4. Схема прогоняется через `DatabaseManager.createDatabase(name, schema, description)` →
     реальный локальный файл `databases/<имя>.db`, регистрация в `store`, запись в `db_logs`.
  5. Результат: число таблиц/записей, авто-открытие просмотра БД.
- Вручную схему по‑прежнему можно ввести, но наличие файлов делает создание основным/точным.

**2.3 Создание из чата при подгрузке файлов**
- `ChatView` уже умеет прикладывать «📎 Файлы»; дополняется логика в `Agent.processTask`:
  - при детекте типа создания БД и **прикреплённых файлах** → ассистент **реально вызывает**
    `DatabaseManager.createDatabase` на сгенерированной из файлов схеме (а не только возвращает
    текст-схему, как сейчас);
  - имя БД — из запроса пользователя или авто;
  - после создания возврат в чат («БД создана: таблиц N, записей M»), БД регистрируется и появляется в чипах.
- Это закрывает расхождение статуса «Создание БД из чата = Готово» в таблице ревью с фактическим поведением.

**2.4 Удаление и гигиена**
- При удалении БД (Настройки → 🗑️, удаление из чата/реестра) дополнительно удалять локальный файл
  `databases/<имя>.db` и `db_logs` для этого имени (чинит разрыв «осиротевших» файлов/логов).

**Учёт «А.1»**: помнить про `lib/` без `slf4j` — до добору драйвера реальный SQLite в песочнице не
поднимается (в тестах splitSql — SKIP). Приоритет ВАЖЕН как запрос пользователя 🔴.

## ✅ Сделано в этой сессии — Этап A2 «Управляемый agentic-цикл записи в БД»

> Терминал-компиляция — exit 0; smoke-тест расширен до **14 проверок (OK)**.

**Задача A2 (🔴):** уйти от хрупкого механизма «LLM сама вставит ```sql```-блок / autoExecuteSqlUpdates»
и дать агенту детерминированный безопасный контур *чтение → запись → подтверждение* через function calling.

**Реализовано:**

- **Встроенные управляемые функции `db_query` / `db_execute`** (`ToolExecutor`):
  - показываются модели только когда выбрана активная БД (`hasActiveDatabase`);
  - **`db_query`** — строго чтение: `SELECT / PRAGMA / WITH / EXPLAIN`; выдаёт колонки + строки;
  - **`db_execute`** — безопасная запись (`INSERT / UPDATE / DELETE / CREATE …`):
    `UPDATE`/`DELETE` **без `WHERE` отклоняются**, транзакционные `BEGIN/COMMIT/…` и `PRAGMA`
    не допускаются; выполняется только против активной (выбранной) БД;
  - компактный формат результата для повторной подачи модели;
  - детерминированные private-охранники (`isReadStatement`, `guardWrite`, `hasSqlWhere`…),
    покрытые новыми проверками smoke-теста.
- **Активация в `Agent.processTask` (A2-контур):**
  - при выбранной БД (`dbPath`+`dbName`) function calling включается даже без пользовательских
    чипов и в `tools` добавляются `db_query`/`db_execute`;
  - маршрутизация tool_call: встроенные функции идут в `ToolExecutor.executeBuiltinSql`,
    пользовательские — как и раньше в `ToolExecutor.execute`; счёт использования фиксируется обоего;
  - **после tool-контура `autoUpdateDb` принудительно выключается** — нет двойной записи
    (и через `db_execute`, и через авто-парсинг ```sql``` из ответа).
- **Системный промпт БД переписан** под A2: сначала `db_query` (проверка фактов), затем
  `db_execute` (точечная запись с обязательным `WHERE`), потом подтверждение пользователю.

**Smoke-тест:** `test/corpagent/SmokeCoreTest.java` → добавлен `testA2DbGuards()` (8 проверок:
`db_query` принимает SELECT/PRAGMA и отклоняет запись; `db_execute` отклоняет UPDATE/DELETE без
`WHERE` и `PRAGMA`, разрешает INSERT и UPDATE с `WHERE`). Итог **14/14 OK** (2 splitSql — SKIP).

**Ограничения среды для живого прогона A2 (не закрыто кодом, а окружением):**
- В `lib/` нет **`slf4j`**, а `SqliteHelper.<clinit>` требует драйвер sqlite → живое открытие БД
  в этой песочнице падает (`NoClassDefFoundError: org/slf4j/LoggerFactory`). Это **существующая
  недоукомплектовка портируемого дистрибутива**: перед сдачей добавьте в дистрибутив `slf4j-api`
  (+ `slf4j-simple` для логов), иначе функции реального SQLite (в т.ч. новые `db_query/db_execute`,
  схема, авто-DML) заработают не полностью.
- Финальное ручное подтверждение DML в UI не входило в данную сессию — кандидат в следующий блок
  (расширить `db_execute` политикой «query → подтвердить → apply» либо флаг allow-user-confirm).

## 4. Токены и деньги: важные оговорки

**Стоимость разработки** (токены на генерацию кода): ≈ **6–7 млн токенов** → при 20 млн = 1 $ **≈ $0.32** (диапазон до ~$0.45).

**Про суточные лимиты модели:**
- Написание кода идёт через ИИ-сессии и **не расходует API-лимит приложения**.
- Рабочий лимит приложения (уточняется по тарифу провайдера, DeepSeek «Rate & spend»):
  - типичный запрос ≈ 4–15K токенов; **без бюджета контекста** может доходить до 40–60K → риск выхода за окно 64K.
  - при ~40 запросах/день × ~8K ≈ 320K токенов/день ≈ **$0.016/день** эксплуатации.
- Без Этапа A1 длинный диалог способен **превысить 64K-окно** → ошибка API. Поэтому **A1 — обязательная база** для работы под реальные дневные лимиты. Реализация A1 (обрезка контекста) + D (бюджет/алерты) гарантирует работу без упора в лимит и без перерасхода.
